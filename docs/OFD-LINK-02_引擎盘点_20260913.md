## 二、凭证与账户模型盘点

### 2.1 履约号生成规则（服务端收口）

- 函数：`nextDocNo(prefix:'O'|'F'|'J')`（`server/db.ts`）。
- 格式：`${prefix}-${YYYYMM}-${NNNN}`，4 位序列，按月重置；序列存 `id_seq` 表，key=`O-202609` 等，`INSERT ... ON CONFLICT DO UPDATE` 自增。
- 种子基线：`O-202609=89 / F-202609=41 / J-202609=102`。
- 消息号 `M<ts><seq>`。
- **与百泰动线对齐度**：规则本身与「bybt-ofd 履约号」诉求兼容；是否需要品牌前缀（如 bybt 前缀）/跨线全局唯一，待总管定版（见 G6）。

### 2.2 本地账户实体结构（当前：独立 SQLite，非底座）

表（`server/db.ts`，better-sqlite3）：

- `dus(id,type,name,vcaseId)` —— 8 个 DU，type ∈ `H/C/E/D/T/Y` 六帽（C/E 各 2 个）。
- `hus(id,name,duId,title,role,passHash,oas_identity_id)` —— 操作层身份；13 个种子（bcrypt 密码，内测统一）；`oas_identity_id` 为 OAS 外键（轻量迁移补列 + 索引）。
- `orders / ofds / jobs / msgs / id_seq`（JSON 列内嵌 deliverables/trace/attachments）。

角色枚举：`requester / assignee / duAdmin / operator / observer / sysAdmin`。

> ⚠️ **与纪律冲突点**：总管要求**零新表、复用底座 `organizations`/`user_organizations`（13u 纪律）**。当前 bybt-ofd 是**独立 SQLite + 本地 dus/hus 表**，无底座组织表。这不是「新表」问题（存量），而是**账户主数据归属不同源**——见缺口 G1（最高优先）。

### 2.3 认证方式现状（对照本窗刚完成的 quick-login + JWT 体系，注明可复用项）

## 三、身份互通现状（OAS JWKS / /org/me / 缺口）

### 3.1 OAS JWKS 验签 —— **已实现（基础设施就绪），但默认关闭且 claims 口径不符**

`server/oas.ts`：

- **模式**：`OAS_MODE=off`（默认）| `on`。on 时本地登录/quick-login 之外的受保护路由全部走 RS256，fail-closed。
- **验签**：
  - 公钥二选一：`OAS_PUBLIC_KEY`（PEM）或 JWKS（`OAS_JWKS_URL`，缺省拼 `${OAS_BASE_URL}/.well-known/jwks.json`）。
  - **kid 默认 `oas-rsa-001`**（`OAS_KID` 可覆盖）——与总管给的 kid 一致 ✅。
  - JWKS 缓存 TTL 10min，`jwkToPem` 转换 RSA n/e；出站 `fetch` 带 5s `AbortSignal` 超时（与 STAB 互调 5s 口径一致）。
  - 可选校验 `OAS_ISS` / `OAS_AUD`。
  - 当前进程实测：`mode=off, keySource=none`（**未配置 OAS_BASE_URL/JWKS，未连任何 OAS，未碰生产库**）。
- **签发方**：本窗**不签发 OAS token**（后端不签发，符合纪律）；仅验签 + 解析。

### 3.2 组织身份查询 `/api/v1/org/me` —— **未实现（核心缺口）**

- 全仓检索：**无 `/api/v1/org/me`、无 `organizations`/`user_organizations` 表、无任何向底座/ERP 的出站组织查询**（仅 OAS JWKS 拉取一处出站）。
- 当前 `resolveIdentity()` 直接从 **JWT claims** 推导组织身份：
  - 读 `claims.identity_id / role / sub_role / ms_access / du_id / name`；
  - `ms_access` 正则匹配 H/C/E/D/T/Y 帽 → 本地 `dus`；`ROLE_MAP` 映射 12u 角色；
  - JIT upsert 本地 `hus`（id=`OAS-<identityId>`，带 `oas_identity_id` 外键），未知角色/无法定位 DU → fail-closed。

> 🔴 **关键契约冲突（G2）**：定版明确「身份互通=同一份 OAS JWT + **GET /api/v1/org/me 查组织身份，禁加 JWT claims**」。当前实现把 DU 帽/角色/组织放在自定义 claims（`ms_access/du_id/role/sub_role`），**违背「禁加 claims」**。正确做法：JWT 只携带标准身份标识（`sub`/`identity_id` 等标准 claim），**组织归属（HDU/个人版-经营版、DU 帽、角色）一律经 `/org/me` 实时查询底座**，再映射到本地 HU 缓存。

### 3.3 身份互通缺口列明

1. **G2**：无 `/api/v1/org/me` 客户端（出站 GET + 5s 超时 + 缓存 + 降级策略）。
2. **G3**：`resolveIdentity` 依赖自定义 claims，需改为「标准 claim 定身份 + `/org/me` 定组织」。
3. **G4**：JWKS issuer 现未知（`zhdjcdwnhv` 的 base URL / `OAS_ISS`/`OAS_AUD` 未配置），需要 OAS 发布物的实际 `issuer` 与 JWKS URL（kid 已知 `oas-rsa-001`）。
4. 本地 `hus` JIT provisioning 与底座 `user_organizations` 的映射/同步策略未定（缓存有效期、离职/换帽回收）。

- 接收已认证 HDU（同一份 OAS JWT）；
- 经 `/org/me` 解析组织身份，映射/缓存为引擎内部 DU/HU 执行身份；
- 仅在内测缺底座时，用 `quick-login` 演示身份兜底（已具备）。

是否需要 bybt-ofd **内置** `quick-register`（作为注册动线的落地窗之一），请总管在打通方案中明确（G7）。

## 六、一句话结论

bybt-ofd 引擎的**三单状态机/三红灯/48h 自动验收/逐项验收退回返工/直发 B/履约号生成/RS256 验签骨架均已在 main 实码就绪且经过冒烟**；要并入百泰动线，**主干工作是「身份与账户去本地化」**：把组织身份来源从本地 SQLite + JWT 自定义 claims，切换为**底座 `organizations`/`user_organizations` + `GET /api/v1/org/me`（同一份 OAS JWT，kid `oas-rsa-001`）**，并补履约回执事件钩子；`quick-register` 是否在引擎落地待总管裁定。本窗未改任何业务码、未碰 OAS 生产库、未加 JWT claims。
